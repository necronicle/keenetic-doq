DNS-over-QUIC (RFC 9250) для роутеров Keenetic — **вместо** штатных DoT/DoH,
не трогая порт 53.

KeeneticOS умеет DoT и DoH, но не DoQ, и добавлять его не планирует.
Существующие решения (AdGuard Home, dnsproxy) требуют `opkg dns-override`:
захватывают порт 53, вытесняют штатный `ndnproxy` и ломают соседние
Entware-проекты. `keenetic-doq` работает иначе:

```
клиенты LAN → ndnproxy :53 → <LAN-IP>:5354 (doqd) → [кеш] ─┬ геоблокированное имя → закреплённый сервер обхода (quic://)
                                                            └ остальное → быстрейший из серверов (quic://)
```

Демон `doqd` слушает обычный DNS на LAN-адресе роутера (порт 5354) и
регистрируется штатной командой `ip name-server <LAN-IP>:5354` как апстрим
системного DNS. Порт 53 никто не трогает, `opkg dns-override` не нужен.

У doqd две полосы. Имена геоблокированных сервисов (ChatGPT, Claude,
Gemini…) резолвит один закреплённый сервер обхода (по умолчанию geohide
или dns-ai): он отдаёт адреса своих прокси, и все домены сервиса получают
прокси одной страны. Все остальные имена идут в самый быстрый из серверов.

> Данный проект предназначен для исследования сетевых протоколов и изучения работы DNS. Используется исключительно в учебных целях.

## Когда роутер спрашивает doqd

Для KeeneticOS doqd — обычный DNS-сервер, прописанный вручную. Какой
сервер ответит клиенту, решает штатная логика роутера:

- **Включены DoT/DoH — doqd не используется вообще.** По
  [справке Keenetic](https://support.keenetic.ru/ultra/kn-1811/ru/31543.html)
  все запросы тогда идут только на серверы DoT/DoH, а DNS провайдера и
  прописанные вручную серверы, в том числе doqd, не используются. Запасного
  переключения на них нет — это подтвердилось и у пользователей. Поэтому
  DoT/DoH для работы doqd нужно выключить.
- **DoT/DoH выключены — запрос уходит сразу на все обычные серверы**:
  doqd, DNS провайдера и другие прописанные вручную, а клиент получает
  самый быстрый ответ
  ([справка Keenetic](https://support.keenetic.ru/ultra/kn-1811/ru/22961.html)).
  DNS провайдера оставить можно, но тогда часть ответов придёт от него, и
  какая именно — заранее не предсказать. Чтобы всё шло через doqd,
  отключите DNS провайдера в настройках подключения к интернету
  («игнорировать DNS провайдера», в CLI — `interface <имя-подключения> ip
  no name-servers`), затем `system configuration save`. После этого DNS
  роутера работает, только пока жив doqd.

Устройства с профилем интернет-фильтра (AdGuard DNS, Яндекс.DNS, SkyDNS)
ходят в DNS фильтра, мимо doqd.

## Возможности

- DoQ-клиент по RFC 9250: живые QUIC-соединения (стрим на запрос,
  переиспользование, keep-alive, TLS-возобновление), ID=0 на проводе.
- Несколько адресов у сервера: дозвон идёт лесенкой по всем, мёртвый адрес
  не задерживает живой; удачный запоминается.
- Гео-полоса для обхода геоблокировок: серверы обхода (`geo`, по умолчанию
  geohide и dns-ai) оцениваются один раз по живости и скорости TLS до их
  прокси; лучший закрепляется и меняется только при отказе. Геоблокированные
  имена — из встроенного списка (OpenAI, Anthropic, Gemini/AI Studio,
  NotebookLM, xAI), свои (`geo-domain`) и найденные автоматически — идут
  только на него. Адреса прокси закреплённого сервера проверяются раз в
  30 с, мёртвые и медленные отфильтровываются из ответов.
- Быстрая полоса: все остальные имена идут в быстрейший живой сервер из
  `upstream` и `geo` (по умолчанию Quad9 и ControlD плюс серверы обхода); если
  тот не ответил за ~3× своего обычного времени, тот же запрос параллельно
  уходит следующему. Мёртвый сервер не съедает время запроса и не встаёт
  снова первым — вернёт его фоновая проверка. Все серверы пробуются при
  старте. Резервные (`fallback`, по умолчанию нет) спрашиваются, только
  когда отказали все остальные.
- Соединение, переставшее отвечать (например, после переподключения WAN),
  проверяется и заменяется новым; медленный ответ одного запроса его не рвёт.
- Кеш ответов по TTL с LRU-вытеснением; одинаковые одновременные запросы
  уходят наружу один раз. Если апстримы недоступны или тянут дольше 1,8 с,
  отдаётся устаревший ответ из кеша (RFC 8767, до суток, с TTL 30 с).
- CLI-утилита в том же бинарнике: `doqd add/remove/list/test/status/geo`,
  `add-domain`/`remove-domain` — свои DoQ-серверы и геоблокированные домены
  без правки файлов, с живой проверкой до применения.
- Статические бинарники без зависимостей.

## Требования

Keenetic с установленным [Entware](https://help.keenetic.com/hc/ru/articles/360000925139)
и пакетом `curl` (`opkg install curl`) — он нужен для скачивания.
Встроенный в busybox `wget` на Keenetic собран без TLS и `https://` не
открывает, поэтому именно curl. Всё остальное, что использует doqd и его
скрипты, входит в busybox и есть всегда.

| Архитектура Entware | Бинарник |
|---|---|
| `aarch64-*` | `doqd-linux-arm64` |
| `mipsel-*` | `doqd-linux-mipsle` |
| `mips-*` (BE) | `doqd-linux-mips` |

## Установка одной командой

На роутере (по SSH):

```sh
curl -fsSL https://raw.githubusercontent.com/necronicle/keenetic-doq/main/install.sh | sh
```

Инсталлер: определяет архитектуру, скачивает бинарник из релиза и сверяет
SHA256, ставит `/opt/sbin/doqd`, пишет конфиг `/opt/etc/doqd.conf`
(подставляя LAN-адрес) и автозапуск `/opt/etc/init.d/S56doqd`, запускает
демона и регистрирует name-server. Существующий конфиг при переустановке
не перезаписывается; конфиги старых версий инсталлер переводит на ключ
`geo` сам (повторный запуск на конфиге 0.4.0 ничего не меняет).

Оффлайн-вариант (бинарник уже скопирован на роутер):

```sh
sh install.sh --local ./doqd-linux-arm64
```

## Управление апстримами

Всё управление — тем же бинарником, без правки файлов руками:

```sh
~ # doqd list
GEO — geo-blocked names go only to the pinned server, marked * (/opt/etc/doqd.conf):
   1. quic://geohide.ru                          alive  rtt 212 ms  proxies 4/4 alive, tls 176 ms
 * 2. quic://dns.dns-ai.ru                       alive  rtt 317 ms  proxies 4/4 ok, tls 102 ms
FAST — every other name goes to the fastest of these and the servers above:
   3. quic://dns.quad9.net                       alive  rtt 209 ms
   4. quic://p0.freedns.controld.com             alive  rtt 186 ms

listen: 192.168.1.1:5354   daemon: running (pid 11236)
```

Секция GEO — серверы обхода, звёздочка отмечает закреплённый; FAST —
остальные имена идут в быстрейший из этих серверов и серверов GEO. Резервные
серверы (если есть) помечаются `[fallback]`.

Закреплённый сервер, рейтинг и состояние его прокси:

```sh
~ # doqd geo
pinned:     quic://dns.dns-ai.ru (since 2026-10-09 12:34)
evaluation: 2026-10-09 12:34

RANKING (last evaluation):
 1. quic://dns.dns-ai.ru               coverage 3/3  proxies 2/2 alive  tls 128 ms
 2. quic://geohide.ru                  coverage 3/3  proxies 4/4 alive  tls 176 ms

PINNED SERVER PROXIES (checked every 30 s):
  13.140.94.151                            healthy  tls 102 ms
  160.79.104.10                            healthy  tls 82 ms
  2607:6bc0::10                            healthy  tls 85 ms
  62.60.230.61                             healthy  tls 148 ms

learned geo-blocked names: 0
```

`doqd geo reselect` переоценивает серверы обхода сразу, не дожидаясь отказа
(ждёт до 45 с и показывает новый выбор). После `doqd add --geo` выбор сам не
пересматривается — сохранённый закреплённый сервер переживает рестарт, —
так что новый сервер оценит только `doqd geo reselect`.

Проверить любой сервер, ничего не меняя:

```sh
~ # doqd test quic://dns.quad9.net
probing quic://dns.quad9.net
  bootstrap  2 address(es) from 1.1.1.1:53 over udp in 25 ms: 149.112.112.112, 9.9.9.9
  connect    149.112.112.112:853  OK in 145 ms
  query      keenetic.com A  answered in 43 ms
OK — answered in 215 ms
```

Добавить свой сервер — с живой проверкой до записи в конфиг (мёртвый
сервер случайно не попадёт; обходится флагом `--force`). Без флагов сервер
попадёт в `upstream` (быстрая полоса), с `--geo` — в серверы обхода, с
`--fallback` — станет резервным:

```sh
~ # doqd add --fallback quic://dns10.quad9.net
probing quic://dns10.quad9.net ... OK (198 ms)
added to /opt/etc/doqd.conf as fallback #6
restarting the daemon ... alive (pid 20702)
```

Удалить — по номеру из `list` или по URL (последний сервер `geo`/`upstream`
удалить нельзя):

```sh
~ # doqd remove 6
removed fallback quic://dns10.quad9.net
restarting the daemon ... alive (pid 20702)
```

Свой геоблокированный домен (с поддоменами) — в гео-полосу; встроенный
список при этом остаётся:

```sh
~ # doqd add-domain example.com
~ # doqd remove-domain example.com
```

Диагностика одной командой:

```sh
~ # doqd status
daemon:          running (pid 11236, uptime 3m30s)
listen:          192.168.1.1:5354 (udp+tcp)
geo:             pinned dns.dns-ai.ru since 2026-10-09 12:34, proxies 4/4 healthy
registration:    present in KeeneticOS name-servers
resolve via doqd: NOERROR, 0 ms
resolve via :53:  NOERROR, 0 ms
```

## Конфигурация — `/opt/etc/doqd.conf`

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `listen` | `<LAN-IP>:5354` | адрес:порт слушателя (UDP+TCP) |
| `geo` | `quic://geohide.ru`, `quic://dns.dns-ai.ru` | сервер обхода геоблокировок, строка на сервер: геоблокированные имена идут только на закреплённый из них; остальные имена они тоже могут отдавать (быстрая полоса). Первая строка `geo`, `upstream` или `fallback` отменяет дефолты всех трёх ключей |
| `upstream` | `quic://dns.quad9.net`, `quic://p0.freedns.controld.com` | обычный DoQ-сервер, строка на сервер: остальные имена идут в быстрейший живой из `upstream` и `geo` |
| `fallback` | нет | резервный DoQ-сервер: спрашивается, только когда отказали все `geo` и `upstream`; TTL его ответов урезается до 60 с. Нужен хотя бы один `geo` или `upstream` |
| `geo-domain` | нет | свой геоблокированный домен (с поддоменами), строка на домен, сверх встроенного списка. Удобнее `doqd add-domain` |
| `bootstrap` | `77.88.8.8`, `77.88.8.8:1253`, `8.8.8.8`, `1.1.1.1` | обычные DNS-серверы для резолва имён апстримов; только IP (порт можно указать). Опрашиваются все сразу, молчащий по UDP переспрашивается по TCP; ответ кешируется на его TTL |
| `cache_size` | `4096` | максимум записей кеша |
| `min_ttl` / `max_ttl` | `60` / `86400` | границы TTL кеша, сек |
| `log` | `info` | debug / info / warn / error |

Закреплённый сервер хранится в `/opt/var/lib/doqd/geo.state` и переживает
рестарт.

Через `doqd add`/`doqd remove`/`doqd add-domain` демон перезапускается автоматически; после
ручной правки — `/opt/etc/init.d/S56doqd restart`.

## Проверка работы

Всё нужное делает `doqd status` — он резолвит и напрямую через doqd, и
через штатный `:53`, показывает закреплённый сервер обхода и проверяет
регистрацию (пример вывода — выше, в «Управлении апстримами»).

Регистрация подробно и доказательство, что трафик реально идёт по QUIC:

```sh
ndmc -c 'show ip name-server'        # штатная утилита, есть всегда
tcpdump -ni any 'udp port 853'       # нужен пакет: opkg install tcpdump
```

`dig` в Entware тоже не входит: либо `opkg install bind-dig`, либо
запускайте его с компьютера в той же сети:

```sh
dig @192.168.1.1 -p 5354 example.com   # прямо в doqd, повтор — из кеша
dig @192.168.1.1 example.com           # сквозной путь через штатный DNS
```

## FAQ

**Почему такие дефолты, а не AdGuard?** geohide и dns-ai — серверы
обхода геоблокировок: для ChatGPT, Gemini, Claude и других сервисов,
закрытых для России, они отдают адреса своих прокси, поэтому геоблокированные
имена идут только на них. Quad9 и ControlD таких адресов не знают и отдают
настоящие; для остальных имён они наравне с серверами обхода: запрос идёт в
самый быстрый. AdGuard DNS в ряде сетей РФ блокируется ТСПУ и по DoQ, и по
DoT — `doqd test quic://dns.adguard-dns.com` покажет таймаут рукопожатия, а
держать в дефолтах заведомо мёртвый сервер незачем. Проверьте свои: `doqd
list` пробует каждый сервер живым запросом. Сервер обхода, недоступный у
вашего провайдера, работе не мешает — запросы его обходят, — но его можно
убрать: `doqd remove <номер>`.

**Куда делся comss?** Убран из дефолтов в 0.3.5. doqd тогда выбирал сервер
с самым быстрым DNS-ответом, и это обычно был comss, но его прокси для
геоблокированных сервисов оказались самыми медленными: TLS-рукопожатие с
chatgpt.com через них занимало от 0,2 до 4,7 с, через dns-ai — 0,13–0,15 с.
Сайт открывался заметно дольше, хотя DNS отвечал быстро. С 0.4.0 скорость
прокси учитывается при выборе сервера обхода, а медленные прокси закреплённого
сервера отсекает фильтр. Вернуть comss можно: `doqd add --geo
quic://dns.comss.one`. Инсталлер убирает строку `upstream
quic://dns.comss.one` только при обновлении с 0.3.x и только если в конфиге
остаётся другая строка `upstream`; иначе comss переходит в `geo`.

**Геоблокированный сервис (ChatGPT, Gemini…) не открывается.** Сначала
обновитесь до 0.4.0: раньше doqd брал самый быстрый ответ, и домены одного
сайта получали прокси разных серверов, а быстрый DNS не значил быстрых
прокси. Инсталлер сам переведёт конфиг на ключ `geo`. Затем посмотрите
`doqd geo`: закреплённый сервер, живость и TLS его прокси. Если прокси
мертвы, а замена не произошла, `doqd geo reselect` переоценит серверы сразу.
Если домена нет во встроенном списке и doqd не определил его сам —
добавьте: `doqd add-domain <домен>`. После правки перезапустите на
устройствах браузер: старые соединения и кеш устройств держат прежние
адреса. Ещё посмотрите `doqd status`: строка `other DNS` значит, что у
роутера кроме doqd прописаны и другие серверы, и настоящий адрес может
прийти мимо doqd. Чтобы всё шло через doqd, отключите DNS провайдера — см.
[«Когда роутер спрашивает doqd»](#когда-роутер-спрашивает-doqd).

**Как doqd отличает геоблокированное от обычного?** Три источника.
Встроенный список — OpenAI, Anthropic, Gemini/AI Studio, NotebookLM, xAI.
Свои домены — `geo-domain` в конфиге или `doqd add-domain`. И автоопределение:
для неизвестного имени doqd смотрит ответ закреплённого сервера, и если в
нём адреса из пула прокси этого сервера, имя считается геоблокированным
и дальше идёт только на него. Классифицируются прямо только A-запросы; для
AAAA, HTTPS и других типов doqd сначала делает внутренний A-запрос. Раз
выученное имя остаётся геоблокированным до рестарта: позднее «обычное»
решение его не отменяет. В HTTPS/SVCB-ответах для геоблокированных имён doqd
вырезает подсказки `ipv4hint`/`ipv6hint`: в них может быть настоящий адрес
сервиса, и браузер пошёл бы по нему мимо прокси. Если на такой запрос не
ответил ни один сервер обхода, doqd отвечает пустым ответом (NODATA), а не
ответом обычного резолвера, — браузер возьмёт адреса из A/AAAA. Пул прокси сервера пополняется только ответами на
три пробных домена (chatgpt.com, claude.ai, gemini.google.com), а не на
каждое гео-имя: иначе имя из списка, которое сервер не подменяет (например,
x.ai с настоящими адресами Cloudflare), затянуло бы в гео-полосу все сайты
Cloudflare. Обычные сайты поэтому получают настоящие адреса от самого быстрого
сервера, а пинг до них не зависит от серверов обхода.

**Как doqd выбирает сервер обхода и почему не прыгает между ними?** При
первом запуске (и по `doqd geo reselect`) doqd оценивает каждый `geo`-сервер:
живость и медиану TLS-рукопожатия до его прокси на chatgpt.com, claude.ai и
gemini.google.com. Лучший по охвату и скорости закрепляется; серверы,
у которых медиана TLS в пределах 20 % от лучшей, считаются равными и
сохраняют порядок из конфига — поэтому выбор не скачет из-за шума замеров.
Закреплённый сервер меняется только при отказе: три ошибки подряд на A/AAAA
(SERVFAIL и REFUSED тоже считаются; ошибки на HTTPS/SVCB — нет: geohide
сбрасывает такие запросы всегда) или все его прокси мертвы три проверки подряд
(проверки — раз в 30 с). Перед переключением doqd проверяет сеть запросом через
быструю полосу: если и она молчит, виноват не сервер, а сеть, и закреплённый
остаётся. Оценка, в которой ни один сервер ничего не обошёл (обычно лежит
интернет), безрезультатна: прежний выбор и рейтинг остаются, `geo.state` не
переписывается, а оценка повторяется через 1 мин, 2, 4… до 30 мин. Выбор хранится в
`/opt/var/lib/doqd/geo.state` и переживает рестарт; если оценку прервал
shutdown, она не сохраняется, а повреждённый `geo.state` вызывает новую
оценку. Если у закреплённого сервера прокси стал мёртвым или медленным,
кешированные ответы с ним сбрасываются сразу — когда рядом в ответе есть
здоровый адрес того же типа (ответ, где плохи все адреса, фильтр всё равно
отдаёт как есть).

**Как откатиться на 0.3.x?** Версии 0.3.x не знают ключа `geo` и с конфигом
0.4.0 не запустятся. Перед установкой старой версии верните в
`/opt/etc/doqd.conf` строки `geo` в `upstream`, а строки `upstream` с Quad9 и
ControlD — в `fallback`; или удалите `/opt/etc/doqd.conf`, и инсталлер
старой версии создаст свой дефолтный.

**Как добавить свой геоблокированный домен?** `doqd add-domain example.com`
— домен и его поддомены пойдут на закреплённый сервер обхода; демон
перезапустится сам. Убрать — `doqd remove-domain example.com` (встроенные
домены остаются). Вручную — строка `geo-domain example.com` в
`/opt/etc/doqd.conf` и `/opt/etc/init.d/S56doqd restart`.

**Дефолтные серверы что-то фильтруют.** `dns.quad9.net` блокирует
малварные домены (ControlD `p0` не
фильтрует ничего). Вариант без
блокировок — `doqd add quic://dns10.quad9.net` (и `doqd remove` для
`dns.quad9.net`); `quic://unfiltered.adguard-dns.com` — если AdGuard у
вас доступен.

**`ndmc: system failed [0xcffd0062]` / `Cli::Main: failed to initialize`,
а `doqd status` пишет `registration: NOT found` или `registration: unknown`.**
Это не про doqd — он установлен и работает. Так выглядит установка из
шелла, открытого командой `exec sh` внутри штатного CLI роутера (SSH на
порт 22, логин admin, затем `exec sh`): сессия CLI уже занята, и `ndmc`
не может открыть вложенную, поэтому инсталлер не смог прописать
name-server, а `doqd status` из того же шелла не может это проверить. Вы
уже в CLI роутера — `ndmc` вам не нужен. Наберите `exit`, чтобы вернуться
к приглашению `(config)>`, и выполните там:

```
ip name-server <LAN-IP>:5354
system configuration save
show ip name-server
```

Те же команды можно дать в Web CLI (`http://<адрес-роутера>/a`), а
`ndmc` и `doqd status` нормально работают из Entware-сессии — SSH на
порт 222, логин root. Пока регистрации нет, запросы идут мимо doqd —
через штатный DNS.

**После перезагрузки роутера пропал интернет: IP пингуются, имена не
резолвятся, а `doqd list` пишет `lookup dns.comss.one on 127.0.0.1:53:
i/o timeout`.** Это баг версий до 0.3.0. doqd резолвил имена своих апстримов
системным резолвером, а на Keenetic это `127.0.0.1` — тот самый DNS роутера,
в списке серверов которого прописан сам doqd. Пока WAN поднят, на запрос
отвечают серверы провайдера; на загрузке, пока соединение не установлено,
doqd остаётся единственным name-server-ом, и его собственный запрос про
`dns.comss.one` возвращается ему же. DNS роутера встаёт колом. Лечится
обновлением: `curl -fsSL
https://raw.githubusercontent.com/necronicle/keenetic-doq/main/install.sh | sh`
— начиная с 0.3.0 имена апстримов резолвятся через отдельные
`bootstrap`-серверы, минуя DNS роутера. Конфиг править не нужно, но если
внешний 53-й порт у вашего провайдера закрыт, пропишите свои:
`bootstrap <IP>` в `/opt/etc/doqd.conf`.

**После перезагрузки роутера doqd не поднимается.** С версии 0.2.5 демон
дожидается своего адреса: на загрузке `/opt` монтируется раньше, чем
интерфейс получает адрес, и одиночная попытка bind раньше убивала демона
насовсем (init-скрипт Entware повторных попыток не делает). Если и на
0.2.5 не поднимается — посмотрите `doqd status`: когда адрес из `listen`
не поднят ни на одном интерфейсе, он скажет об этом прямо. Обычно это
значит, что LAN-адрес роутеру выдаёт вышестоящий DHCP (режим Relay) и
после перезагрузки он сменился: пропишите роутеру постоянный LAN-адрес,
поправьте `listen` в `/opt/etc/doqd.conf` и перерегистрируйте
`ip name-server <новый-адрес>:5354`.

**Почему порт 5354, а не 5353?** 5353 на Keenetic занят avahi-daemon
(mDNS).

**Почему LAN-адрес, а не 127.0.0.1?** KeeneticOS не принимает loopback в
`ip name-server` (`Dns::Manager: invalid IP address`).

**В `doqd list` апстрим down с `bootstrap lookup ...: no bootstrap server
answered`.** Сам DoQ-сервер может быть вполне жив: doqd не узнал его адрес.
Ни один bootstrap-сервер не ответил на обычный DNS-запрос с именем этого
апстрима — ни по UDP, ни по TCP. Если при этом другие апстримы живы, почти
наверняка провайдер выбрасывает DNS-запросы на 53-й порт с именами сервисов
обхода блокировок. Помогает bootstrap на другом порту — у Яндекс DNS это
1253. В новых установках он уже прописан; в старом конфиге добавьте строку
`bootstrap 77.88.8.8:1253` в `/opt/etc/doqd.conf` и выполните
`/opt/etc/init.d/S56doqd restart`. Проверить руками: `nslookup <имя> 77.88.8.8`
молчит, а `doqd test quic://<имя>` после правки отвечает. До 0.3.2 в этой
ситуации ошибка называла последний сервер из списка (`1.1.1.1:53: dial udp
... i/o timeout`), хотя он был ни при чём.

**В `doqd list` апстрим down с `dial ...: context deadline exceeded` или
`no address answered`.** Адрес сервера нашёлся, но QUIC-соединение
(udp/853) не установилось. `doqd test quic://<имя>` покажет по шагам, какие
адреса пробовались и чем кончилось. Если сервер работает из других сетей,
почти наверняка его блокирует провайдер — так бывает с серверами обхода
блокировок и с AdGuard. doqd тут ничего не сделает; на работу DNS это не
влияет: с 0.3.3 недоступный апстрим уходит в конец очереди и не задерживает
запросы (до 0.3.3 он раз в 30 секунд вставал первым, и пачка запросов
получала SERVFAIL). Лишний сервер можно убрать: `doqd remove <номер>`.

**Добавил сервер, а он down.** `doqd list` показывает живость и RTT
каждого апстрима; `doqd remove <номер>` убирает лишний. При добавлении
`doqd add` сам проверяет сервер и не даст записать мёртвый без `--force`.

## Удаление

```sh
curl -fsSL https://raw.githubusercontent.com/necronicle/keenetic-doq/main/uninstall.sh | sh
```

Снимает регистрацию name-server, останавливает и удаляет демон. Конфиг
`/opt/etc/doqd.conf` остаётся.

## Сборка из исходников

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -ldflags "-s -w" -o doqd ./cmd/doqd
# mipsel/mips: GOARCH=mipsle|mips GOMIPS=softfloat
```

## Ограничения

- Шифруется участок «роутер → внешний резолвер» — тот, который видит
  провайдер. Внутри LAN устройства обращаются к роутеру обычным DNS: doqd
  не принимает DoQ-подключения от клиентов локальной сети. Ровно так же
  устроены и штатные DoT/DoH в KeeneticOS.
- Никакой фильтрации и блокировок: что ответил апстрим, то и вернулось
  (кроме отсечённых фильтром мёртвых и медленных прокси сервера обхода).
- doqd слушает только LAN-адрес роутера — наружу (WAN) не торчит.
