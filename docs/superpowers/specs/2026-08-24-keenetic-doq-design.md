# keenetic-doq — DNS-over-QUIC для роутеров Keenetic

Дата: 2026-08-24
Статус: утверждено (дизайн согласован в чате)

## Проблема

KeeneticOS нативно поддерживает DoT и DoH, но не DNS-over-QUIC (RFC 9250),
и добавлять его в прошивку производитель не планирует. Существующие обходные
решения (AdGuard Home, dnsproxy через `opkg dns-override`) захватывают порт 53
и вытесняют штатный `ndnproxy`, ломая соседние проекты (Z2K и др.).

Цель: DoQ-апстрим, который встаёт **рядом** со штатными DoT/DoH, не трогая
порт 53 и системный DNS-прокси.

## Архитектура

```
клиенты LAN → ndnproxy :53 → [штатные DoT/DoH апстримы]
                           → 127.0.0.1:5354 (doqd) → [cache] → quic://апстримы
```

`ndnproxy` сам выбирает быстрейший апстрим; локальный прокси с кешем
почти всегда отвечает первым, поэтому DoQ получает естественный приоритет
без отключения остальных серверов.

## Компонент 1: `doqd` — DoQ-прокси на Go

- Слушает обычный DNS на `127.0.0.1:5354`, **UDP и TCP**.
- Апстримы: список `quic://host[:port]` (порт по умолчанию 853).
  - Живые QUIC-соединения: переиспользование одного соединения для многих
    запросов (по стриму на запрос, 2-байтовый length-prefix по RFC 9250),
    session resumption / 0-RTT при переподключении.
  - Статистика RTT и ошибок по каждому апстриму; запрос уходит в быстрейший
    живой; при ошибке — мгновенный failover на следующий.
  - Фоновый health-check возвращает восстановившиеся апстримы в ротацию.
- Кеш ответов: по TTL записей (floor/cap на разумных значениях), ограничение
  по числу записей с LRU-вытеснением — память роутера бережём.
- Библиотеки: `quic-go` (QUIC), `miekg/dns` (DNS wire format).
  Без зависимостей от AdGuard dnsproxy.
- Конфиг: `/opt/etc/doqd.conf` — адрес/порт слушателя, список апстримов,
  размер кеша, уровень логирования.
- Апстримы по умолчанию: `quic://dns.comss.one` (первый; AdGuard DoQ/DoT
  блокируется ТСПУ — подтверждено смоук-тестом 2026-08-24),
  `quic://unfiltered.adguard-dns.com` (резерв через failover). Прокси сам
  ничего не фильтрует.
- Статические бинарники под все арки Keenetic: aarch64, mipsel, mips (BE).

## Компонент 2: интеграция с Keenetic

- Регистрация в системном DNS: `ip name-server <LAN-IP>:5354` через RCI +
  `system configuration save`. Порт 53 и `ndnproxy` не трогаем.
  - Проверено на живом роутере 2026-08-24: loopback KeeneticOS НЕ принимает
    (`Dns::Manager: invalid IP address: 127.0.0.1`), поэтому doqd слушает
    LAN-адрес роутера (br0), инсталлер определяет его автоматически.
- Автозапуск: init-скрипт `/opt/etc/init.d/S56doqd` (Entware), с respawn.

## Компонент 3: поставка

- `install.sh`: определяет арку, скачивает бинарник из GitHub Releases,
  кладёт конфиг + init-скрипт, запускает, регистрирует name-server.
- `uninstall.sh`: останавливает, снимает регистрацию
  (`no ip name-server 127.0.0.1:5354`), удаляет файлы.
- GitHub Actions: тесты + кросс-сборка статических бинарников, релизы.
- Репозиторий: `keenetic-doq`, приватный, аккаунт necronicle.

## Тестирование

- Go-юниты (TDD): кеш (TTL, LRU), DoQ-кодирование (length-prefix,
  запрет transaction ID по RFC 9250 — ID=0), выбор апстрима и failover.
- Живые тесты на тест-роутере 192.168.1.1 (aarch64):
  1. `dig @127.0.0.1 -p 5354` напрямую в doqd;
  2. сквозной запрос через ndnproxy :53;
  3. подтверждение QUIC-трафика к апстриму (tcpdump udp/853);
  4. перезагрузка роутера — выживание автозапуска и регистрации.
- Помнить: зелёный тест на aarch64 не доказывает работу на MIPS (BE) —
  байтоориентированный код проверяется юнитами на обеих байтовостях.

## Вне объёма

- Собственная фильтрация/блокировки — нет, прокси нейтрален.
- DoQ-сервер (входящий DoQ) — нет, только клиентская сторона.
- Веб-панель — нет; конфиг файлом, статус — логами.
